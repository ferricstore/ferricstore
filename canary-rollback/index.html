import time
from ferricstore import WorkflowClient, complete, transition

client = WorkflowClient.from_url("ferric://127.0.0.1:6388")
flow = client.workflow(type="canary-release", initial_state="canary")

@flow.state("canary")
def canary(ctx):
    @ctx.effect("route-canary", "envoy.route", operation_digest=f"canary:{ctx.id}:v1")
    def route():
        envoy.set_weight("v2.4.0", 10, request_id=f"{ctx.id}:canary:v1")
    route()
    return transition("soak", run_at_ms=int(time.time() * 1000) + 86_400_000)

@flow.state("soak")
def soak(ctx):
    @ctx.effect("promote", "envoy.route", operation_digest=f"promote:{ctx.id}:v1")
    def promote():
        envoy.set_weight("v2.4.0", 100, request_id=f"{ctx.id}:promote:v1")
    promote()
    return complete(result=b"promoted")

@flow.state("rollback")
def rollback(ctx):
    @ctx.effect("rollback", "envoy.route", operation_digest=f"rollback:{ctx.id}:v1")
    def restore():
        envoy.set_weight("v2.3.9", 100, request_id=f"{ctx.id}:rollback:v1")
    restore()
    return complete(result=b"rolled back")

# Datadog can move a waiting soak directly to rollback:
client.signal(
    run_id, signal="5xx", if_state="soak", transition_to="rollback",
    idempotency_key=f"{run_id}:5xx:v1",
)

⚠️ THE HAZARD vs. HOW FERRICSTORE PREVENTS IT

Why Long-Running Canary Deployments Fail & How FerricStore Fixes It

Compare standard Python sleep / cron polling failures with FerricStore's durable quorum timers.

💤

Sleep Thread Exhaustion

💥 The Hazard (Standard Python / Celery):

Calling time.sleep(86400) holds an OS worker thread for 24 hours. Enough concurrent deployments can exhaust the worker pool.

🛡️ How FerricStore Prevents It:

Persisted observation state: schedule the next eligible run without holding an application handler or OS thread open.

📉 Worker Starvation Outage ✓ No Blocked Handler
💥

Server Crash During 24h Soak

💥 The Hazard (In-Memory Sleep):

A Kubernetes node restarts or crashes 18 hours into the canary soak. The in-memory sleep timer vanishes, leaving canary traffic permanently frozen at 10%.

🛡️ How FerricStore Prevents It:

Replicated Timer State: The deadline is stored with the workflow state. After a worker or host failure, due work becomes eligible again according to the configured lease and recovery behavior.

🚨 Stuck Production Deployments ✓ Lease-Based Recovery
⚡

Late Rollback Double-Drop

💥 The Hazard (Custom Scripts / Cron):

When 5xx errors spike at hour 20, the script tries to rollback while a second deployment pipeline starts, causing conflicting Envoy route updates.

🛡️ How FerricStore Prevents It:

Explicit state transitions: protect Envoy routing updates with stable operation digests or provider idempotency and reject stale state writes with fencing.

🚨 Broken Envoy Routing Loop ✓ Guarded Rollback Effect
📈

Silent Metric Degradation

💥 The Hazard (Polling Scripts):

Background polling scripts miss a brief Datadog latency spike due to cron drift, allowing broken code to roll out to 100% of production users.

🛡️ How FerricStore Prevents It:

Application-owned webhook: A Datadog webhook handler can call client.signal(...) with an idempotency key and if_state="soak", advancing the parked workflow to its explicit rollback state.

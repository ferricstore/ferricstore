# Durable closure + state boundary
from ferricstore import FlowClient

client = FlowClient.from_url("ferric://127.0.0.1:6388")
job = client.start_and_claim(
    "order-8492", type="checkout-saga",
    initial_state="charge", worker="checkout-1",
)

# The closure may retry before its result commits, so keep this key stable.
job, charge = client.step(
    job,
    name="charge-customer:v1",
    run=lambda: {
        "id": stripe.Charge.create(
            amount=15000, idempotency_key=f"{job.id}:charge:v1",
        ).id,
    },
    to_state="reserve",
)

What Happens in Production When Idempotency & Determinism Aren't Handled?

In distributed backends, worker retries are inevitable (Kubernetes pod evictions, network timeouts, JVM/Node GC pauses, OOM crashes). If your service relies on raw Celery tasks, SQS queues, or naive scripts, retries re-execute completed side-effects, causing severe real-world damage:

💳

1. Double-Billing & Chargeback Penalties

The Failure: Stripe authorizes a $150 payment, but the worker crashes before acknowledging the message. The queue retries from line 1 without an idempotency key, charging the customer a second time ($300 total).

Real-World Impact: Customer files a fraud dispute. The merchant pays a $15.00 chargeback fee per dispute and faces credit card processor suspension.
📦

2. Ghost Inventory Decrements (Over-Selling)

The Failure: Worker runs UPDATE items SET stock = stock - 1 in Postgres. It crashes during the confirmation webhook. The retry re-runs the SQL query, decrementing stock to 8 instead of 9.

Real-World Impact: Physical warehouse inventory desynchronizes from the database ledger. During flash sales, this causes overselling and expensive order cancellations.
🤖

3. Exponential AI Token Waste & 429 Cascades

The Failure: An autonomous AI agent completes a 4,000-token research synthesis ($0.12). A network timeout occurs while uploading the PDF. The retry re-runs the entire LLM prompt from scratch.

Real-World Impact: Redundant token burns double your OpenAI/Anthropic cloud bill and exhaust API rate limits (429 Too Many Requests), crashing downstream services.
📨

4. Notification Storms & Carrier Spam Blocking

The Failure: Worker sends an SMS OTP or order confirmation email, then fails while updating the user record. Every retry re-dispatches the SMS/Email to the end user.

Real-World Impact: Customer receives 5 duplicate text messages in 2 minutes. Carriers flag your Twilio phone number as spam, and support tickets spike.

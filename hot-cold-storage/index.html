THE UNIQUE FERRICSTORE ARCHITECTURE

Hot RAM + Cold NVMe Tiering:
Keep Hot Values in RAM and Cold Values on NVMe

Pure in-memory deployments can become expensive as datasets grow and require an explicit eviction or failure policy under memory pressure. FerricStore can keep hot values in ETS RAM while serving disk-backed values from NVMe. MemoryGuard can release cached RAM values while retaining durable disk records; actual latency, memory use, and cost depend on the workload and deployment.

⚠️ THE HAZARDS OF PURE RAM STACKS

Why In-Memory Databases Fail in Production & How FerricStore Fixes It

Compare standard Redis/Memcached failure modes with FerricStore's hybrid storage tiering.

💸

The Full-Dataset RAM Cost

💥 The Hazard (Redis / Memcached):

As data grows, a pure in-memory deployment needs RAM for the full dataset plus indexes and allocator overhead.

🛡️ How FerricStore Prevents It:

Hot/Cold NVMe Tiering: Keep a bounded working set in RAM while retaining colder values on disk. Benchmark the required hot set before sizing production.

RAM footprint scales with the full dataset ✓ Size the hot set separately
🗑️

Silent LRU Key Eviction

💥 The Hazard (Memory Saturation):

When memory reaches the configured limit, Redis behavior depends on maxmemory-policy: writes may fail or eligible keys may be evicted.

🛡️ How FerricStore Prevents It:

MemoryGuard Disk Protection: FerricStore can demote hot values to disk locators instead of using cache-style eviction. Availability still depends on the configured durability topology and healthy storage.

🚨 Lost Shopping Carts & Sessions ✓ Disk-Backed Demotion
⏱️

Dataset Reload During Recovery

💥 The Hazard (RDB Reload Warmup):

A large in-memory dataset may require reload or reconstruction before the normal hot path is available.

🛡️ How FerricStore Prevents It:

Disk-backed locators: FerricStore can address cold values by file and offset. Recovery time still depends on data files, indexes, hardware, and topology.

Recovery depends on dataset and persistence mode ✓ Direct cold-value addressing
💥

60-Second Async Data Loss

💥 The Hazard (Async Snapshots):

Redis snapshots to disk asynchronously. A sudden power loss or host kernel panic destroys all writes executed in the last 60 seconds.

🛡️ How FerricStore Prevents It:

Configured write boundary: Disk acknowledgment and replication behavior follow the chosen FerricStore topology and durability settings.

🚨 Unsaved Transactions Lost ✓ Configured Durability Policy

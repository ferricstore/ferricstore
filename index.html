Durable workflows.
Built around your code.

FerricStore is an open-source workflow and queue server. It saves each job’s progress and coordinates retries and waiting, so your services can continue work after a restart.

How it works Get started locally

Use Python, Go, TypeScript, Java, or Elixir.
Your application code runs in your own services.

Your services do the work.
FerricStore keeps track.

A workflow is a job with named steps, such as collecting data, writing a summary, and sending a report. FerricStore stores which step is ready, who owns it, and what happens next.

Use it for background jobs, AI agents waiting for approval, or processes spanning services. Start with one job and add steps as it grows.

Read the workflow model →
  1. 1

    Claim a ready step

    A worker in your service gets a temporary claim, called a lease, to process that step.

  2. 2

    Run your application code

    Call a model, generate a report, or contact another service. Your handler runs outside FerricStore.

  3. 3

    Save what happens next

    Complete the job, move to the next named step, retry later, or wait for a signal such as human approval.

What happens to unfinished work after a crash?

After the worker’s lease expires, a replacement can claim the saved state and run its handler. The unfinished handler may run again; previously committed transitions remain recorded. FerricStore does not replay handler code to reconstruct workflow state.

For external actions such as charging a card, use a stable idempotency key with a provider that honors it, and guarded execution where appropriate. Saving workflow progress alone does not make an external action happen exactly once.

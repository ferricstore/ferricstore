Many requests, one expired result:
This example turns 10,000 refreshes into 1 database query

A cache stampede happens when one popular value expires and many requests try to rebuild it at once. In this example, 10,000 requests can reach Postgres together unless the application coordinates them. With FerricStore, the native FETCH_OR_COMPUTE helper lets one worker compute the value while the other 9,999 wait in memory, then releases the stored result. Timing still depends on the workload.

What changes when a popular value expires

These cards describe the same modeled scenario; measure your own workload before sizing production.

💥

Many requests reach the database

Without coordination:

When a popular cache key expires, many web threads can open database connections together, exhaust the Postgres pool, and trigger an outage.

With FerricStore:

Native Atomic Queueing: FETCH_OR_COMPUTE acquires a single in-process compute lease and queues all duplicate requests in memory until the first query finishes.

🚨 Complete Site Outage (504s) ✓ 1 Single DB Connection Used
💸

Illustrative database sizing cost

Illustrative scenario:

A team might model a $5,000/month database tier to absorb a short 2-second surge. This figure is an example, not a measured cost claim.

With FerricStore:

Single-flight refresh: Requests for the same expired key can share one refresh owner while others wait or serve stale data. Size the database from measured workload and failure behavior.

💸 $5,000/Mo Wasted DB Tier ✓ Reduces Duplicate Refresh Load
🛑

Refresh coordination must recover

Without a recovery path:

Developers try to solve dogpiling using Redis locks. If the worker crashes while computing, the lock is stuck and all 10,000 users hang forever.

With FerricStore:

Fenced Timeout Hand-Off: FerricStore automatically expires the compute lease if the worker dies, seamlessly promoting the next queued request to complete the fetch.

🚨 Frozen User Requests ✓ Single-Compute Coordination
⚡

Waiting requests need a result

Polling approach:

Client applications sleep and poll Redis in a loop waiting for the cache to warm up, causing CPU thrashing and network latency spikes.

With FerricStore:

Coordinated waiter release: After the compute callback returns, waiting clients receive the stored value; latency depends on workload and topology.

📉 High P99 Latency Spikes ✓ Coordinated Waiter Release

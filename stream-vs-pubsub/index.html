Live messages or saved messages?
Choose Pub/Sub for now, or Streams for catch-up

With FerricStore, Pub/Sub sends a live message to listeners connected now; it does not save that message for later. Streams save entries and let a consumer group pick up unread work after reconnecting. Run either example to see who receives the message and what a reader can miss.

🎯 USE CASE GUIDE

When to Use Pub/Sub vs. When to Use Streams

Both are native, first-class primitives in FerricStore. Choose the best tool for your application.

📡 USE PUBSUB

Cache Invalidation Across 100 Web Pods

When a user updates their profile or product price, all 100 web nodes must immediately invalidate their local in-memory cache.

Why Pub/Sub fits: Every currently subscribed web pod receives the same ephemeral invalidation without creating a replay log.
client.publish("cache:bust", "product:42")
📜 USE STREAMS

Financial Ledgers & Order Processing

When a customer places an order, the event must be safely stored on disk and processed by inventory and payment workers.

Why Streams fit: Events are persisted through the configured durability topology. After reconnecting, workers continue from their consumer-group position and may redeliver unacknowledged entries.
client.xadd("events:orders", {"id": "1001"})
📡 USE PUBSUB

Live Chat & Dashboard Notification Toasts

Pushing a live notification to a user currently looking at their dashboard or chat window.

Why Pub/Sub fits: Connected users receive the live event, and no historical message queue accumulates.
client.publish("user:42:notifications", "New comment")
📜 USE STREAMS

Multi-Worker Background Task Hand-Offs

Distributing 50,000 video encoding or email generation jobs across 10 background worker instances.

Why Streams fit: Consumer groups (XREADGROUP) share work; unacknowledged entries can be reclaimed under the configured rules.
client.xreadgroup("workers", "w1", {"jobs": ">"})
⚖️ TECHNICAL SPECIFICATIONS

Pub/Sub vs. Streams Capability Comparison

Architectural properties of FerricStore's two native messaging engines.

CAPABILITY 📡 LIVE PUBSUB (PUBLISH / SUBSCRIBE) 📜 DURABLE STREAMS (XADD / XREADGROUP)
Primary Purpose Real-time broadcast: Pushing instant events to active subscribers. Durable event log: Storing sequential events for explicit acknowledgement and replay.
Delivery Semantics At-Most-Once: Delivered directly to active client TCP sockets. At-Least-Once: Persisted to NVMe Raft disk; requires explicit XACK.
Storage & Memory Overhead No replay log: Pub/Sub messages are not retained as stream entries. Compact NVMe Append Log: Bounded disk entries with Hot Keydir pointers.
Worker Load Balancing Fanout Broadcast: Every active subscriber gets the message. Consumer Groups (XGROUP): Work is shared across multiple workers.
Latency Low-latency path: Direct in-memory TCP socket push; measure on the target deployment. Durable append: Commit latency depends on batch shape, durability settings, topology, and hardware.

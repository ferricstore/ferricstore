The Beginner's First Queue:
Durable Background Jobs Without Celery, RabbitMQ, or Redis

Running background tasks often means coordinating a broker, workers, retries, and state. FerricStore exposes a simple lifecycle: Enqueue ➔ Claim ➔ Complete. If a worker crashes, the job becomes claimable after its lease expires; fencing rejects stale state writes. External email or payment calls still need an idempotency key.

Why modern engineering teams replace complex Celery/RabbitMQ clusters with FerricStore queues.

Why Traditional Message Queues Break in Production

Compare standard RabbitMQ/Celery failure modes with FerricStore's durable queue engine.

🧟

The Zombie Duplicate Storm

💥 The Hazard (SQS / RabbitMQ):

Worker #1 pauses during a Java GC cycle. The visibility timeout expires, and Worker #2 picks up the job. Worker #1 wakes up and BOTH charge the customer.

🛡️ How FerricStore Prevents It:

Monotonic Fencing Tokens: Every lease receives an incrementing epoch token. When Worker #1 attempts to finish with stale Token 101, FerricStore rejects the write.

🚨 Duplicate $250 Stripe Charge ✓ Fenced Stale Writes

RabbitMQ Broker OOM Crash

💥 The Hazard (Memory Brokers):

A downstream API outage backs up 500,000 unacknowledged messages in RabbitMQ RAM, crashing the broker and losing queued work.

🛡️ How FerricStore Prevents It:

Disk-backed queue state: FerricStore persists queued jobs through its configured storage and replication topology. Validate capacity and memory use for the intended workload.

🚨 Dropped Background Work ✓ Millions of Jobs on Disk
⏳

5-Minute Visibility Timeout Lag

💥 The Hazard (SQS Visibility Delay):

When a worker crashes, SQS forces the message to wait for the full 5-minute visibility timeout to expire before any other worker can touch it.

🛡️ How FerricStore Prevents It:

Lease-based reclaim: after the active lease expires, another worker can claim the job with a newer fence.

📉 5-Minute Processing Delay ✓ Fenced Hand-Off

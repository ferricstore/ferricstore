WHAT THE NUMBERS MEAN

Choose the execution model first

The useful question is not “which number is larger?” It is “does application code need to run between durable states?”

REAL APPLICATION WORK

54,060 worker-driven workflows/s

Workers claim a named state, run normal application code, and report a durable transition or completion. The measured Azure run used one tiny handler, so it measures orchestration capacity—not the speed of your business logic.

What does 54K mean?

One server started, coordinated, claimed, and durably completed roughly 54,000 one-state synthetic workflows each second while producers and workers ran together.

Actions are billable server operations. Three regular Activities generally consume at least one start Action plus three Activity Actions; retries, timers, Signals, and Heartbeats add more.

What 300K Actions/s could mean: With three regular Activities, a minimal workflow is about four Actions: one Workflow start + three Activity Actions. 300K ÷ 4 = 75K workflows/s is only a derived ceiling if nothing else generates Actions and the Worker fleet keeps up. Temporal does not publish it as workflows/s. Local Activities are counted differently: markers from one Workflow Task are grouped into one Action. Do not apply the four-Action conversion to that shape.
THROUGHPUT IS NOT LATENCY

What we actually know about response time

We now have latency for the fused chain, but not for the Azure worker-driven run.

FERRICSTORE WORKER Unknown 54K Azure run latency percentiles

The Azure run reports throughput and aggregate elapsed time only. ≈18.5 seconds is the service time for all one million workflows—not 18.5 seconds per workflow and not 18.5 milliseconds.

FERRICSTORE FUSED 27 ms p99 for all 3 steps together · p50 18.1 ms
  1. 01

    Start Create the workflow and persist its first named state.

  2. 02

    Advance Persist the second named state in workflow history.

  3. 03

    Finish Persist the final named state and mark the workflow completed.

27 ms covers this entire chain. Per-step latency was not measured, so this result cannot be read as 9 ms per step. No application code runs between these states.

TEMPORAL CLOUD ≈850 ms documented three-Activity baseline

Temporal’s current performance guide gives an approximate three-Activity total latency of 850 ms with regular Activities, about 275 ms with Local Activities, and about 265 ms with Eager Start + Local Activities.

WHY 27 MS DOES NOT “BEAT” 850 MS

One persists states; the other schedules Activities

The FerricStore fused chain performs no application work between its states. Temporal’s example includes three Activity scheduling cycles. The numbers demonstrate different costs, not a winner.

The fair test is worker-driven versus Activity-driven.

Run three no-op FerricFlow state handlers against three no-op Temporal regular Activities with matched payloads, deployment distance, load, and durability. Report throughput and full latency tails.
